
# GitHub Desktop 사용법

## 1. 개요

개발을 하다 보면 파일을 잘못 수정하거나 삭제하는 등 예상하지 못한 사고가 발생할 수 있다. 또한 여러 사람이 같은 프로젝트를 작업할 때는 서로의 작업 내용을 관리하고 공유할 방법이 필요하다.

**Git**은 파일의 변경 이력을 기록하고 관리할 수 있게 해주는 버전 관리 시스템이다.

Git을 사용하면 다음과 같은 작업이 가능하다.

- 프로젝트의 변경 이력 저장
- 이전 버전으로 복구
- 여러 기능을 독립적으로 개발
- 팀원들과 작업 내용 공유
- 코드 변경 사항 비교

하지만 Git은 기본적으로 터미널 명령어를 사용하기 때문에 처음 접하면 어렵게 느껴질 수 있다.

**GitHub Desktop**은 Git의 주요 기능을 그래픽 인터페이스로 사용할 수 있게 해주는 프로그램이다. 이번 글에서는 GitHub와 GitHub Desktop의 기본적인 사용법을 정리한다.

---

## 2. Repository 생성

Repository, 줄여서 **레포지토리**는 프로젝트 파일과 변경 이력이 저장되는 공간이다.

레포지토리는 GitHub 홈페이지와 GitHub Desktop에서 모두 생성할 수 있다.

GitHub 홈페이지에서는 기본적으로 초록색 **New** 버튼을 눌러 새로운 레포지토리를 생성할 수 있다.

레포지토리를 생성할 때는 다음 항목들을 설정할 수 있다.

- 레포지토리 이름
- 레포지토리 설명
- 공개 범위
- README 파일 생성 여부
- `.gitignore` 파일
- 라이선스

### README

`README.md`는 프로젝트에 대한 설명을 작성하는 마크다운 파일이다.

일반적으로 다음과 같은 내용을 작성한다.

- 프로젝트 소개
- 설치 방법
- 실행 방법
- 사용 기술
- 주의 사항

### .gitignore

`.gitignore`는 Git이 추적하지 않을 파일이나 폴더를 지정하는 파일이다.

예를 들어 Visual Studio 프로젝트에서는 빌드 결과물이나 사용자별 설정 파일을 제외하기 위해 사용한다.

### License

라이선스는 다른 사람이 해당 프로젝트의 코드를 어떤 조건으로 사용할 수 있는지를 명시한다.

---

GitHub Desktop에서도 다음 메뉴를 통해 레포지토리를 생성할 수 있다.

```text
File → New repository
```

GitHub Desktop에서 생성한 레포지토리는 처음에는 로컬 컴퓨터에만 존재한다.

따라서 GitHub에 업로드하려면 **Publish repository** 버튼을 눌러 원격 레포지토리를 생성해야 한다.

레포지토리를 생성한 후에는 링크를 공유하거나 GitHub의 협업자 관리 메뉴를 통해 팀원을 초대할 수 있다.

---

## 3. Fetch, Commit, Push, Pull

GitHub Desktop을 사용할 때 가장 자주 접하게 되는 기능은 다음 네 가지이다.

- Fetch
- Commit
- Push
- Pull

각 기능이 서로 비슷하게 느껴질 수 있지만 역할은 명확하게 구분된다.

---

### Fetch

**Fetch**는 원격 레포지토리에 새로운 변경 사항이 있는지 확인하는 작업이다.

GitHub Desktop에서 **Fetch origin** 버튼을 누르면 GitHub에 새로운 커밋이 있는지 확인한다.

Fetch는 변경 사항을 바로 내 프로젝트에 적용하지 않는다. 원격 저장소의 상태를 확인하고 새로운 변경 이력이 있다는 사실만 가져온다.

변경 사항이 발견되면 버튼이 **Pull origin**으로 변경된다.

쉽게 말하면 Fetch는 새로고침 또는 업데이트 확인과 비슷하다.

---

### Commit

**Commit**은 현재까지 작업한 변경 사항을 로컬 Git 저장소에 기록하는 작업이다.

게임의 세이브 포인트와 비슷하다고 생각할 수 있다.

GitHub Desktop의 **Changes** 메뉴에서는 다음과 같은 변경 사항을 확인할 수 있다.

- 새로 추가된 파일
- 수정된 파일
- 삭제된 파일
- 파일 내부에서 변경된 코드

커밋을 생성할 때는 다음 내용을 작성할 수 있다.

- Summary: 커밋 내용 요약
- Description: 자세한 변경 내용

커밋 메시지는 나중에 변경 이력을 확인할 때 사용되므로 무엇을 수정했는지 알아볼 수 있도록 작성하는 것이 좋다.

예시는 다음과 같다.

```text
플레이어 이동 기능 추가
```

```text
인벤토리 아이템 삭제 오류 수정
```

```text
몬스터 클래스 구조 변경
```

커밋은 현재 선택된 브랜치에 저장되며, 아직 GitHub에는 업로드되지 않은 상태이다.

---

### Push

**Push**는 로컬에서 생성한 커밋을 GitHub의 원격 레포지토리에 업로드하는 작업이다.

정리하면 다음과 같다.

```text
Commit = 로컬에 변경 이력 저장
Push = 저장한 변경 이력을 GitHub에 업로드
```

Push를 하면 현재 선택된 레포지토리와 브랜치에 커밋이 업로드된다.

따라서 협업 중에는 현재 어떤 브랜치에 있는지 확인하지 않고 Push하지 않도록 주의해야 한다.

특히 여러 사람이 사용하는 `main` 브랜치에 직접 Push하면 아직 완성되지 않았거나 오류가 있는 코드가 프로젝트 전체에 적용될 수 있다.

---

### Pull

**Pull**은 GitHub의 원격 레포지토리에 있는 변경 사항을 내 로컬 프로젝트로 받아오는 작업이다.

다른 팀원이 Push했거나 다른 컴퓨터에서 프로젝트를 수정한 경우 Pull을 통해 최신 변경 내용을 가져올 수 있다.

쉽게 말하면 다운로드와 비슷하지만, 단순히 파일을 내려받는 것이 아니라 Git의 변경 이력을 기준으로 현재 프로젝트에 변경 사항을 병합한다.

원격 레포지토리에 내가 가지고 있지 않은 커밋이 존재하면 바로 Push할 수 없는 경우가 있다.

이때는 먼저 Pull을 진행해 원격 변경 사항을 가져온 후 Push해야 한다.

일반적으로 작업을 시작하기 전에는 다음 순서로 확인하는 것이 안전하다.

```text
Fetch → Pull → 작업 시작
```

## 4. Branch

레포지토리를 처음 생성하면 일반적으로 `main` 또는 `master`라는 브랜치가 생성된다.

이 브랜치는 프로젝트의 기준이 되는 **기본 브랜치(Default Branch)**이다.

**Branch**는 독립적인 작업 공간을 만드는 기능이다.

Branch는 나뭇가지라는 뜻으로, 하나의 프로젝트에서 새로운 작업 흐름을 분리해 만든다고 생각할 수 있다.

예를 들어 현재 정상적으로 작동하는 게임 프로젝트가 있다고 가정해 보자.

여기에 인벤토리 기능을 추가하기 위해 기존 코드를 바로 수정했는데 오류가 발생하면 프로젝트 전체가 실행되지 않을 수 있다.

이때 새로운 브랜치를 만들어 작업하면 기존 `main` 브랜치는 유지하면서 인벤토리 기능을 별도로 개발할 수 있다.

```text
main
 └─ feature/inventory
```

브랜치는 주로 다음과 같은 목적으로 사용한다.

- 새로운 기능 개발
- 버그 수정
- 코드 구조 개선
- 실험적인 기능 테스트
- 팀원별 작업 공간 분리

---

### Branch 생성하기

GitHub Desktop 상단의 **Current branch** 메뉴를 누른 후 **New branch**를 선택하면 새로운 브랜치를 생성할 수 있다.

브랜치 이름은 해당 브랜치에서 어떤 작업을 하는지 알아보기 쉽게 작성하는 것이 좋다.

예시는 다음과 같다.

```text
feature/inventory
```

```text
feature/player-attack
```

```text
fix/monster-spawn
```

```text
refactor/item-system
```

브랜치를 생성하면 GitHub Desktop의 현재 브랜치가 새로 생성한 브랜치로 변경된다.

이후 생성되는 커밋은 `main`이 아니라 현재 선택한 브랜치에 저장된다.

---

### Branch 변경하기

GitHub Desktop 상단의 **Current branch** 메뉴에서 원하는 브랜치를 선택하면 작업 브랜치를 변경할 수 있다.

다만 아직 Commit하지 않은 변경 사항이 존재할 때 브랜치를 변경하면 문제가 생길 수 있다.

GitHub Desktop에서는 상황에 따라 다음 중 하나를 선택할 수 있다.

- 변경 사항을 현재 브랜치에 남기기
- 변경 사항을 이동할 브랜치로 가져가기
- 변경 사항을 먼저 Commit하기

일반적으로는 현재 작업 내용을 Commit한 후 브랜치를 변경하는 것이 안전하다.

---

### Branch Publish

로컬에서 새 브랜치를 생성하면 해당 브랜치는 아직 내 컴퓨터에만 존재한다.

GitHub에 브랜치를 업로드하려면 **Publish branch** 버튼을 눌러야 한다.

```text
로컬 브랜치 생성
→ 작업
→ Commit
→ Publish branch
```

브랜치를 한 번 Publish한 이후에는 새로운 커밋을 Push하는 방식으로 업데이트할 수 있다.

---

## 5. Merge

브랜치에서 기능 개발이 완료되었다면 해당 내용을 `main` 브랜치에 합쳐야 한다.

이처럼 한 브랜치의 변경 사항을 다른 브랜치에 합치는 작업을 **Merge**라고 한다.

예를 들어 `feature/inventory` 브랜치의 내용을 `main`에 합치려면 먼저 `main` 브랜치로 이동한다.

그다음 GitHub Desktop에서 다음 메뉴를 선택한다.

```text
Branch → Merge into current branch
```

목록에서 `feature/inventory` 브랜치를 선택하면 해당 브랜치의 변경 사항이 현재 브랜치인 `main`에 병합된다.

병합 전에는 다음 항목을 확인하는 것이 좋다.

- 기능이 정상적으로 작동하는가?
- 컴파일 오류가 없는가?
- 불필요한 파일이 포함되지 않았는가?
- 다른 기능에 영향을 주지 않는가?
- 필요한 커밋이 모두 Push되었는가?

협업 프로젝트에서는 직접 `main`에 병합하기보다 GitHub의 **Pull Request**를 사용하는 것이 일반적이다.

---

## 6. Pull Request

**Pull Request**, 줄여서 PR은 한 브랜치의 변경 사항을 다른 브랜치에 병합해 달라고 요청하는 기능이다.

예를 들어 `feature/inventory` 브랜치의 작업이 끝났다면 다음과 같이 요청할 수 있다.

```text
feature/inventory → main
```

Pull Request에서는 다음 내용을 확인할 수 있다.

- 어떤 파일이 변경되었는지
- 어떤 코드가 추가되거나 삭제되었는지
- 작성된 커밋 목록
- 팀원의 리뷰와 의견
- 병합 가능 여부

일반적인 협업 흐름은 다음과 같다.

```text
브랜치 생성
→ 기능 개발
→ Commit
→ Push
→ Pull Request 생성
→ 코드 리뷰
→ Merge
```

Pull Request를 사용하면 다른 팀원이 변경 내용을 검토한 후 `main` 브랜치에 반영할 수 있으므로 직접 Push하는 것보다 안전하다.

---

## 7. Conflict

두 사람이 같은 파일의 같은 부분을 서로 다르게 수정하면 Git이 어떤 내용을 적용해야 할지 판단하지 못할 수 있다.

이러한 상황을 **Merge Conflict**, 즉 병합 충돌이라고 한다.

예를 들어 기존 코드가 다음과 같다고 가정한다.

```cpp
int playerHp = 100;
```

한 사람은 다음과 같이 수정했다.

```cpp
int playerHp = 150;
```

다른 사람은 같은 줄을 다음과 같이 수정했다.

```cpp
int playerHp = 200;
```

이 경우 Git은 어느 값을 선택해야 하는지 알 수 없기 때문에 충돌이 발생한다.

충돌이 발생하면 파일에 다음과 비슷한 표시가 나타날 수 있다.

```text
<<<<<<< HEAD
int playerHp = 150;
=======
int playerHp = 200;
>>>>>>> feature/player
```

위쪽은 현재 브랜치의 내용이고, 아래쪽은 병합하려는 브랜치의 내용이다.

필요한 코드를 직접 선택하거나 두 코드를 적절히 합친 다음 충돌 표시를 삭제해야 한다.

수정이 끝나면 파일을 저장하고 GitHub Desktop에서 충돌 해결을 완료한 뒤 Commit한다.

충돌을 줄이려면 다음 습관이 도움이 된다.

- 작업 시작 전에 Pull하기
- 기능별로 브랜치 나누기
- 너무 많은 내용을 한 번에 수정하지 않기
- 작은 단위로 자주 Commit하기
- 팀원과 수정할 파일을 미리 공유하기

---

## 8. Clone

GitHub에 이미 존재하는 레포지토리를 내 컴퓨터로 가져오는 작업을 **Clone**이라고 한다.

GitHub Desktop에서는 다음 메뉴를 사용한다.

```text
File → Clone repository
```

Clone할 레포지토리와 저장 위치를 선택하면 프로젝트 파일과 Git 변경 이력이 함께 다운로드된다.

협업 프로젝트에 처음 참가하거나 다른 컴퓨터에서 작업을 시작할 때 주로 사용한다.

Clone과 Pull의 차이는 다음과 같다.

```text
Clone = 레포지토리 전체를 처음 내려받기
Pull = 이미 받은 레포지토리를 최신 상태로 갱신하기
```

---

## 9. 기본 작업 순서

혼자 작업할 때는 다음과 같은 순서로 사용할 수 있다.

```text
Fetch
→ Pull
→ 파일 수정
→ 변경 사항 확인
→ Commit
→ Push
```

협업하면서 새로운 기능을 개발할 때는 다음과 같은 흐름이 안전하다.

```text
main 브랜치로 이동
→ Fetch
→ Pull
→ 새로운 브랜치 생성
→ 기능 개발
→ Commit
→ Push 또는 Publish branch
→ Pull Request 생성
→ 코드 리뷰
→ Merge
```

작업이 끝난 브랜치는 필요에 따라 삭제할 수 있다.

---

## 10. 주의할 점

### 현재 브랜치 확인하기

Commit이나 Push를 하기 전에는 반드시 현재 선택된 브랜치를 확인해야 한다.

잘못된 브랜치에서 작업하면 변경 내용이 예상하지 않은 위치에 저장될 수 있다.

### Commit과 Push를 혼동하지 않기

Commit만 하면 변경 사항은 내 컴퓨터에만 저장된다.

다른 컴퓨터나 팀원이 변경 내용을 확인하려면 Push까지 해야 한다.

### 작업 시작 전에 Pull하기

오래된 프로젝트 상태에서 작업하면 다른 팀원의 변경 사항과 충돌할 가능성이 높아진다.

작업을 시작하기 전에 Fetch와 Pull을 진행하는 것이 좋다.

### 중요한 파일이 .gitignore에 포함되지 않았는지 확인하기

`.gitignore`에 등록된 파일은 Commit 대상에 나타나지 않는다.

새로 만든 파일이 GitHub Desktop의 Changes 목록에 표시되지 않는다면 `.gitignore`에 포함되어 있는지 확인해야 한다.

### Visual Studio 프로젝트 파일 확인하기

Visual Studio에서 새로운 `.cpp` 또는 `.h` 파일을 추가했는데 다른 팀원의 프로젝트에서 보이지 않는다면 다음 파일이 함께 변경되었는지 확인해야 한다.

```text
.vcxproj
.vcxproj.filters
```

실제 소스 파일만 Push하고 프로젝트 설정 파일을 Push하지 않으면 다른 컴퓨터의 Solution Explorer에 파일이 표시되지 않을 수 있다.

## 11. 정리

GitHub Desktop에서 가장 기본적인 개념은 다음과 같다.

```text
Repository = 프로젝트와 변경 이력을 저장하는 공간
Commit = 변경 사항을 로컬에 기록
Push = 로컬 커밋을 GitHub에 업로드
Fetch = 원격 저장소의 새로운 변경 사항 확인
Pull = 원격 저장소의 변경 사항을 로컬에 적용
Branch = 독립적인 작업 공간
Merge = 서로 다른 브랜치의 작업 내용을 합치기
Clone = 원격 레포지토리를 처음 내려받기
Conflict = 서로 다른 변경 내용이 충돌한 상태
```

처음에는 각 용어가 비슷하게 느껴질 수 있지만 다음 흐름을 기억하면 이해하기 쉽다.

```text
Pull로 최신 내용을 받고
→ Branch에서 작업하고
→ Commit으로 저장하고
→ Push로 업로드하고
→ Merge로 합친다.
```
